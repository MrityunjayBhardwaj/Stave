Publishing to the Community Gallery needs you to sign in with GitHub or Google. Browsing, playing, saving and private links never do. Your profile shows the account you signed in with (your GitHub handle, or "Google account"), and your email stays private: Stave keeps it only to contact you about what you publish.

This page is for people **running their own copy of Stave**. On the hosted site it is already set up.

## What happens without it

Each provider is offered only when its settings are present. Set up GitHub, Google, or both. With neither (or with no `AUTH_SECRET`), sign-in is off: the menu says so, the Publish dialog explains it, and the server refuses to publish with a plain reason. Everything else keeps working.

## Environment variables

| Variable | What it is |
| --- | --- |
| `AUTH_SECRET` | A long random string that signs the session cookie. Make one with `openssl rand -base64 33`. Required. |
| `AUTH_GITHUB_ID`, `AUTH_GITHUB_SECRET` | The GitHub OAuth app's Client ID and a client secret. |
| `AUTH_GOOGLE_ID`, `AUTH_GOOGLE_SECRET` | The Google OAuth client's ID and secret. |
| `AUTH_URL` | Only off Vercel: your site's public origin, e.g. `https://stave.example.com`. (Or set `AUTH_TRUST_HOST=true` if your proxy sets the host header correctly.) |

Sessions live in that signed cookie, so there is no session database to run.

## The callback URLs

Each provider sends people back to one URL on your site. Use your public origin in place of `<origin>`:

- GitHub: `<origin>/api/auth/callback/github`
- Google: `<origin>/api/auth/callback/google`

For local development the origin is `http://localhost:3000`. Most people make a separate GitHub app for local work, because a GitHub OAuth app takes only one callback URL.

## Create the GitHub OAuth app

1. On GitHub, go to **Settings › Developer settings › OAuth Apps › New OAuth App**. (For an organisation, it's the organisation's settings.)
2. **Homepage URL**: your origin. **Authorization callback URL**: `<origin>/api/auth/callback/github`.
3. Register it, copy the **Client ID** into `AUTH_GITHUB_ID`, then **Generate a new client secret** and put it in `AUTH_GITHUB_SECRET`.

Stave asks GitHub only for `read:user user:email`: your public profile and your email address.

## Create the Google OAuth client

1. In the Google Cloud console, pick or create a project, then open **APIs & Services › OAuth consent screen**. Choose **External**, fill in the app name, support email and your site's domain, and add the scopes `openid`, `email` and `profile`.
2. Google's consent screen asks for a **privacy policy URL** (and a home page). You need a privacy policy page on your site before you can publish the consent screen beyond test users.
3. Go to **APIs & Services › Credentials › Create credentials › OAuth client ID**, type **Web application**.
4. **Authorised JavaScript origins**: your origin. **Authorised redirect URIs**: `<origin>/api/auth/callback/google`.
5. Copy the client ID into `AUTH_GOOGLE_ID` and the secret into `AUTH_GOOGLE_SECRET`.

<Aside type="caution">
A privacy policy page is needed for Google sign-in, and is good practice for GitHub too: it should say that Stave keeps the email of the account you sign in with, privately, to contact you about what you publish, and shows your public name, GitHub handle and avatar on your profile. Stave doesn't ship one; write your own.
</Aside>

## Why sign-in is a full-page redirect

Stave sends `Cross-Origin-Opener-Policy: same-origin` on every page, which it needs for audio and visuals that share memory across threads. That header cuts a pop-up window off from the page that opened it, so a pop-up sign-in could never report back. Signing in leaves the page, goes to GitHub or Google, and comes back, reopening the Publish dialog if that's where you started.

## Gallery admins (moderation)

Anyone can report a gallery entry. Admins read those reports and decide: take the entry down, or dismiss the reports and leave it up. An admin is a **signed-in account** you list in one variable:

| Variable | What it is |
| --- | --- |
| `STAVE_GALLERY_ADMINS` | Comma-separated account ids, each `provider:id`, for example `github:12345,google:110248495921238986420`. Spaces around entries are ignored. Unset or empty means nobody is an admin. |

Older versions used a shared `STAVE_GALLERY_ADMIN_KEY` sent as a header. That is gone: the header is ignored, so remove the variable when you set `STAVE_GALLERY_ADMINS`.

### Finding your account id

Sign in to your Stave with the account you want to make an admin, then open `<origin>/api/gallery/me` in the same browser. It answers with JSON; your id is `user.accountId`, already in the `provider:id` form the variable wants:

```json
{ "user": { "name": "Ada", "accountId": "github:12345", ... }, "isAdmin": false }
```

Only you see your own id there (the page never shows it to anyone else). Add it to `STAVE_GALLERY_ADMINS`, redeploy (or restart the server), reload `/api/gallery/me`, and `isAdmin` reads `true`.

### What admins see

With an admin signed in, the Community Gallery gets a **Moderation** tab. It lists every reported entry with each report's reason, and for each one:

- **Open** shows the entry, as anyone would see it.
- **Take down** removes it for everyone. Stave asks why.
- **Dismiss** clears its reports and leaves it up. Stave asks why.

Below that is the **action log**: the newest 200 take-downs and dismissals by any admin, each with who did it (name and account id, never the email), when, and the reason they typed. Only admins can read it. Nobody else sees the tab, and the moderation routes answer `403` to everyone else.

An admin can also take down a whole collection by sending `DELETE /api/gallery/collections/<id>` with the JSON body `{ "reason": "…" }` while signed in; that is logged the same way. Deleting your *own* entry or collection is an ordinary author delete and needs no reason.

## Testing without GitHub or Google

For development and automated tests there is a test-only sign-in that signs in as whatever account id you type. It is on only when the server runs with `STAVE_AUTH_TEST_LOGIN=1` **and** is not a production build; a production build never offers it, whatever the variable says.

```sh
STAVE_AUTH_TEST_LOGIN=1 AUTH_SECRET=dev-only-secret npm run dev
```

A test account's id is `test-login:<what you typed>`, so `STAVE_GALLERY_ADMINS=test-login:gallery-admin` makes the test account `gallery-admin` an admin.

## Limits and the "are you human" check

Anything anyone can write to needs a few guard rails. Stave has three layers, and only the first two live in the code.

### Per-account limits

Each signed-in account (or, for things you can do signed out, each address) may do each kind of write only so many times an hour:

| What | Limit | Counted per |
| --- | --- | --- |
| Publish to the gallery | 10 an hour | account |
| Report an entry | 20 an hour | account, or address when signed out |
| Edit a profile or a collection (make, change or delete) | 60 an hour, together | profile |
| Make a private link | 30 an hour | account, or address when signed out |
| Bring this browser's shares into your account | 250 shares an hour | account |

Windows are fixed hours on the clock, so the count starts over on the hour. Over the limit, the server answers `429` with a plain message ("you've published 10 times in an hour…; try again in 23 minutes") and a `Retry-After` header in seconds, and the dialog shows that message.

Bringing shares into your account counts each share, not each request: every entry, every private link and the old profile counts one (an empty request still counts one). One request carries at most 50 entries and 50 links, so the hour's 250 covers two full requests. If a browser holds more than that, it sends the first 50 of each and the rest on later visits. Counting shares rather than requests matters because moving each share is several storage operations; counting requests let one account move thousands of shares an hour.

Each server keeps its own count, and checks for one account run one at a time, so however many requests arrive at once, one server never lets more than the limit through. The servers also share a small private record per account and kind of write in the gallery's Blob store, and each one counts from whichever is higher, its own count or the record's. That keeps the limit across servers for requests spread over time. Blob can't do an atomic "add one if under the limit", though, so a burst that lands on several servers at the same moment can get the limit's worth through on each of them. When the gallery moves to a database the shared count becomes atomic and that gap closes, with nothing else changing.

Addresses are never stored as they are, only as a keyed hash. If the store can't be reached, the request is not refused for that (it's logged), but each server's own count still applies, so an outage never means no limit at all.

To raise a limit without a code change, set `STAVE_RATE_LIMIT_<NAME>` to a whole number: `STAVE_RATE_LIMIT_PUBLISH`, `_REPORT`, `_EDIT`, `_LINK` or `_CLAIM`. The tests use this; production should normally leave them unset.

### Cloudflare Turnstile on publish and report

[Turnstile](https://developers.cloudflare.com/turnstile/) is Cloudflare's check that most people pass without doing anything. When it is set up, a small widget appears in the Publish dialog and the Report dialog, and the server checks its answer before accepting either. A failed check is refused with `403` and a plain message; if Cloudflare can't be reached, the server says so (`503`) rather than letting the request through.

| Variable | What it is |
| --- | --- |
| `NEXT_PUBLIC_TURNSTILE_SITE_KEY` | The widget's site key. Public; it is built into the page, so set it before building. |
| `TURNSTILE_SECRET_KEY` | The widget's secret key. Server only. |

Leave both unset and nothing changes: no widget, no check. Set both, or neither.

To get keys:

1. In the Cloudflare dashboard, open **Turnstile** and select **Add widget**.
2. Give it a name, add your site's hostname under **Hostname management**, and choose **Managed** as the widget mode.
3. Select **Create**, then copy the site key into `NEXT_PUBLIC_TURNSTILE_SITE_KEY` and the secret key into `TURNSTILE_SECRET_KEY`.

For local work, use Cloudflare's [test keys](https://developers.cloudflare.com/turnstile/troubleshooting/testing/), which work on any hostname including `localhost`:

| Site key | Secret key | Result |
| --- | --- | --- |
| `1x00000000000000000000AA` | `1x0000000000000000000000000000000AA` | always passes |
| `2x00000000000000000000AB` | `2x0000000000000000000000000000000AA` | always fails |

```sh
NEXT_PUBLIC_TURNSTILE_SITE_KEY=1x00000000000000000000AA \
TURNSTILE_SECRET_KEY=1x0000000000000000000000000000000AA \
STAVE_AUTH_TEST_LOGIN=1 AUTH_SECRET=dev-only-secret npm run dev
```

The widget works with the cross-origin isolation headers Stave sends (see above): Cloudflare serves both its script and the widget's frame with headers that allow an isolated page to load them, so no extra setting is needed.

### Per-address Firewall rules (outer layer)

The limits above count per account. In front of them, add per-address rate limits in your host's firewall, so a flood is turned away before it reaches Stave at all. On Vercel: open the project's **Firewall**, select **Configure › + New Rule**, add the conditions below, choose **Rate Limit** as the action, **Fixed Window**, key **IP**, and keep the default **429**. Then **Review Changes › Publish**. (Hobby and Pro windows can be at most 10 minutes.)

| Rule | Method | Path | Limit |
| --- | --- | --- | --- |
| Publish | `POST` | equals `/api/gallery` | 10 per 10 minutes |
| Report | `POST` | matches `^/api/gallery/[^/]+/report$` | 20 per 10 minutes |
| Claim | `POST` | equals `/api/gallery/claim` | 10 per 10 minutes |
| Private links | `POST` | equals `/api/share` | 10 per 10 minutes |
| Every other gallery write | `POST`, `PUT` or `DELETE` | starts with `/api/gallery/` | 60 per 10 minutes |
| Revoking links | `DELETE` | starts with `/api/share/` | 30 per 10 minutes |

These live in the project's Firewall settings, not in the repository, so a new deployment elsewhere needs them added again.
